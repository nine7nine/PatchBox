PatchBox

A patchbay for JACK and PipeWire, a jackdbus server control panel and an NSM session manager in one Rust application, drawn with its own OpenGL renderer on a static, Wayland-only, patched SDL3. It edits JACK's graph and PipeWire's own, never mixed; drives the JACK server through jackdbus and PipeWire's clock and devices through PipeWire's tools; and runs sessions of NSM clients and plain programs. It is built alongside JackBus and uses what that adds, and works as well with PipeWire alone (pipewire-jack), another jackdbus or a plain jackd. Its ideas come from the patchbays and session managers before it — Patchage, Catia, PatchMatrix's matrices, qjackctl, NSM and RaySession among them — reworked with a look and a session format of its own.

The rule behind its shape: PatchBox is never in the audio path. Its JACK clients have no process callback, so jack2 starts no realtime thread for them and never schedules them in the graph; connections, metadata and server settings go through libjack's control side and jackdbus's D-Bus interface. The window sleeps until something happens — one wake a second at idle, no frames — and the session daemon is a single poll() loop.

1System overview

Two processes of PatchBox's own — the window and the session daemon — between the audio servers they control and the session clients they start. Audio flows only between the clients and the JACK server, through shared memory; PatchBox's channels are all control: libjack's requests and notifications, D-Bus to jackdbus, a Unix socket between window and daemon, OSC to NSM clients, PipeWire's own tools, and Wayland to the compositor.

libjack requests (connect, metadata) JACK notifications D-Bus (jackdbus) control socket (JSON lines) NSM (OSC over UDP) PipeWire tools audio (port buffers) Wayland · GL fork / exec · files PatchBox's processes other programs operating system

Three planes, and PatchBox is in two. The audio plane (pink) is JACK's: clients read and write port buffers in /dev/shm and the engine's RT thread drives them; PipeWire's bridge is one more JACK client. PatchBox never touches it — neither of its JACK clients has a process callback, so jack2 creates no RT thread for them. The control plane is everything else: libjack's request socket and notification thread (connect, disconnect, metadata, graph changes), D-Bus to jackdbus (start, stop, the parameter tree), the control socket between window and daemon, OSC to NSM clients. The display plane is Wayland to KWin and GL on the GPU.

Two processes, one per job. The window is a patchbay and a control panel: it can close and reopen at any time. Sessions belong to patchboxd, which the window starts on demand and which outlives it while a session is open or connection rules exist; patchbox-ctl and a systemd user unit drive it without the window. Both keep a JACK client of their own — the window's for the graph it draws, the daemon's for the connections a session or a rule remembers.

PipeWire is optional. In the set-up PatchBox is built for, it runs on top of jackdbus (module-jackdbus-detect): desktop streams live in PipeWire's graph and reach JACK through the "PipeWire" client's Sink and Source. PatchBox shows that graph only when asked — opened from the PipeWire client — and talks to PipeWire through its own tools (pw-dump, pw-link, pw-metadata, pw-cli), never mixing the two graphs (section 8).

2Processes and threads

Neither process has a thread of its own in JACK's realtime path. The window runs its interface on one thread and gets news from helper threads that only queue and wake it. The daemon runs on one thread and a poll(). The figure follows one event through every thread it touches: a session client starts, the window draws its block, and the daemon puts back the connections the session remembers.

libjack request JACK notification wake (SDL event · eventfd) the RT cycle

Callbacks only queue. Calling back into the server from a notification callback can deadlock jack2, and none of this work needs to be fast. So the callbacks in pbx-jack push an Event and call a waker: in the window it posts one SDL user event (an atomic flag keeps at most one queued), in the daemon it writes to an eventfd whose counter does the same coalescing. Everything else — reading ports, connecting, metadata — happens on the thread that owns the client.

Outside the cycle. The RT lane never waits for PatchBox. A connection made from the window or the daemon is a request handled by jackd's server thread; the engine swaps in the new graph state, and the driver thread picks it up at the start of the next cycle. Neither of PatchBox's clients has a process callback, so jack2 neither creates an RT thread for them nor adds them to the activation order.

3The main loop and the renderer

An audio workstation's patchbay should cost nothing while nothing happens. The loop sleeps until input, a wake from a helper thread, or the earliest of its timers; it draws a frame only when something changed. Idle, that comes to one wake a second (the DSP load and the transport) and no frames.

A frame only on change. Every handler that changes what is shown sets redraw; when it is clear the loop skips the UI pass and the GL work and goes straight back to sleep. Hover is cheap the same way: a mouse move redraws only when the rectangle under the pointer is a different one.

Deadlines, not polling. tick() runs whatever is due and returns the earliest deadline left: the graph rebuild 25 ms after the last change (at most 150 ms after the first), the transport every 100 ms while it rolls and every second when it doesn't (a plain client gets no transport notification, and a sync callback would make it a realtime client), the DSP load every second, a JACK retry every 2 s while there is no server. With no deadline at all it sleeps for an hour.

The window itself. Borderless, transparent and GL; the top bar is the title bar (client-side decorations, with KDE's button side) and moves and resizes through SDL's hit test, so the compositor runs the drag. KWin draws the shadow outside the surface through org_kde_kwin_shadow on SDL's own wl_display. The hints keep the screensaver allowed, give the Wayland app id patchbox for the icon, and load GL through GLVND's libOpenGL.so.0 so no GLX or Xlib enters a Wayland-only process.

4From JACK to a graph

Eleven libjack callbacks feed a queue. Graph-changing events start a short debounce, and when it ends the window takes one snapshot of every port, connection and metadata property. A pure function then turns that snapshot into what the canvas shows. The same Graph type carries PipeWire's graph (section 9), so everything downstream works for both.

JACK notification wake main thread PipeWire source

Snapshot, not patch. The window doesn't keep a graph in step with every notification; it rebuilds from a fresh snapshot once things settle. A snapshot is a few hundred library calls on the main thread, off any realtime path, and it can't drift: a notification lost or reordered can't leave a stale port on the canvas. The event log, the statistics and the xrun counter take the events as they come; only the graph waits.

The model is a function. Model::build(graph, layout, own) depends on nothing else. It returns nodes keyed M: (a client), S: (its capture side) or K: (its playback side), with their ports in display order: JACK's order metadata first, then the names. Naming and stereo pairs follow RaySession's rules (L/R, left/right, 1/2 suffixes; a2j's device prefixes; Ardour's Track/port). The layout file is keyed by the same ids, so positions, names and hidden blocks survive a client restarting with new port ids.

5Three views, one model

The canvas draws the same model three ways. Ports puts a wire per connection between port rows, with signal flowing left to right; Ports ↓ is Luluda's vertical flow; Matrix is PatchMatrix's, with one wire per client pair through a grid of ports. Every canvas — JACK's global one, each session's, PipeWire's — keeps block positions and a camera per view style.

Ports, left to right. The default. A block is a client (or one side of it): its title, then a row per port with inputs on the left edge and outputs on the right. Hardware is split into a capture and a playback block, so signal reads left to right across the canvas. A wire is a bezier per connection; pulling one end off a port moves it, dropping it on empty canvas removes it, and every change is one undo step. No port counts clutter this view: the ports are on the blocks.

Ports, top to bottom. The same blocks turned for vertical flow (Luluda's graph): inputs along the top edge, outputs along the bottom, so sources sit above what they feed. It is the Ports button's second state rather than a separate view. The arrangement is this style's own: a vertical layout and a horizontal one don't suit each other, so switching keeps both.

Matrices. PatchMatrix's view: a block per client and, between a source and a sink that share connections of the shown type, a grid with the source's outputs as columns and the sink's inputs as rows. One wire per client pair enters and leaves at the matrix centre. Click a cell to connect, drag across cells to paint the same state (with Shift the stereo partner follows), pin a matrix to keep it without connections. The type tabs (AUDIO, MIDI, CV, OSC) each have their own matrices; the layout is keyed per type.

6The JACK client

pbx-jack is a small FFI crate over 52 functions of libjack.so, linked dynamically so any JACK2 server works (the box runs JackBus). Both the window and the daemon open a client with it. Neither registers a process callback, a sync callback or a port of its own: they sit next to the graph, not in it.

the cycle requests (socket) notifications

Beside the graph. A JACK2 client gets an RT thread only when it sets a process, thread, sync or timebase callback; then the engine schedules it in the activation order and waits for it every period. PatchBox sets none of them, so its clients exist only on the server thread's side: requests over the socket and a notification thread. Slow work in PatchBox — a GL frame, a D-Bus call, a git snapshot — can't make a period late. That is also why the transport is polled: the transport notification is the sync callback, and it would make the window a realtime client.

7jackdbus: the server, mapped

PatchBox never spawns jackd. The server is jackdbus, and the settings page is built from jackdbus's own parameter tree, so every driver, every engine parameter and every internal client shows with its type, range, default and description. Nothing is hard-coded except the order of sections. One worker thread owns the D-Bus connection, because a StartServer that opens a device can take seconds.

D-Bus method calls D-Bus signals PatchBox jackdbus

Read the tree, show the tree. LoadConfig walks ReadContainer and GetParametersInfo under engine, driver, every drivers/<name> and internals/<name>, then asks each leaf for its value (set or default) and constraint. A constraint with values becomes a choice (devices come with their descriptions), a range becomes a number, a boolean a toggle. Parameters that are set and not at their default are drawn amber and can be reset to the default.

Live, where jackdbus allows it. The master driver can be switched on a running server (SwitchMaster, no restart), and the buffer size changes live: through libjack from this page, through SetBufferSize for presets and sessions. With JackBus, jackdbus's log settings and the CPU wake-up latency limit take effect on the running server too. Slave drivers are the exception: jackdbus takes them only while stopped, so PatchBox stops, changes and starts again and says so. Internal clients load and unload live; jackdbus can't say which are loaded, so the page remembers the ones it loaded.

In place where it can be. Presets and sessions both go through jackcfg::apply. A change limited to what a running jackdbus takes — the ALSA or dummy driver's period, jackdbus's log settings, and the CPU wake-up latency limit it holds (cpu-dma-latency) — is made on the running server, so the applications, PipeWire's bridge and every connection stay. Each such change is checked, because an older jackdbus stores a value and applies it only at its next start: the buffer size is read back with GetBufferSize, and the limit in effect is read from /dev/cpu_dma_latency, the smallest of all requests on the system (reading it holds none). A limit above the one asked for, or a released one still in effect, means that jackdbus didn't apply it, and the server is restarted with the settings already in place.

Why the limit belongs in a preset. Deep CPU idle states can take a millisecond or more to wake from; at small buffer sizes that is enough for the driver's wake-up to miss its period. Holding a low limit (C1 only, say) costs power for as long as it's held. A preset for small-buffer work can carry it, and the next preset, which doesn't, releases it, with the server running throughout.

8JACK, PipeWire, or both

PatchBox follows how the audio stack is set up rather than assuming one. Its JACK client talks to whatever libjack.so reaches, and its jackdbus side to whatever owns org.jackaudio.service. Its PipeWire side reads pw-dump and works out from PipeWire's own objects whether PipeWire runs on top of JACK, serves as the JACK server, or runs beside it. The figure shows the three set-ups and what each page shows in them.

On top of jackdbus. The set-up PatchBox is built for. JackBus owns the card and its driver thread is the clock; PipeWire loads module-jackdbus-detect (from the user's own pipewire.conf, so PatchBox ships no drop-in that would load it twice), appears in JACK as the client "PipeWire", and its JACK Sink and Source drive its graph from JACK's cycle. The bridge (module-jack-tunnel) sets the graph's duration to the frames of each JACK cycle, so PipeWire's quantum is JACK's buffer size, live changes included; default.clock.quantum only matters when PipeWire drives its own graph. The two graphs stay apart: desktop streams live in PipeWire's and reach JACK through the bridge. PatchBox shows PipeWire's graph only when the PipeWire block is opened.

PipeWire alone. With pipewire-jack, JACK programs load PipeWire's libjack.so and become PipeWire nodes. PatchBox's JACK client sees PipeWire's graph as JACK ports, so the patchbay works unchanged. There is no jackdbus, so the JACK tab's server controls step aside. The PipeWire tab notices that its own JACK client is one of PipeWire's (serves_jack) and becomes the server's page, with the clock defaults editable and kept through a pipewire.conf.d drop-in.

JACK alone, or PipeWire beside it. Without the bridge each server has its own device and its own clock. Everything JACK works as with the bridge, and the PipeWire tab is the settings page of a separate server. The patchbay and sessions need only libjack, so a plain jackd works too: only the jackdbus page goes quiet.

9PipeWire's graph and settings

PatchBox has no libpipewire bindings. pw-dump --monitor streams every PipeWire object as JSON and sits idle between changes; a reader thread folds it into an object table. From that table it builds two things: a Graph of the same type JACK's snapshot produces, and a PwState for the settings tab. Writes go back through pw-link, pw-metadata and pw-cli. The child runs only while a PipeWire view or the PipeWire tab is open.

pw-dump stream to the views writes back

Same graph type, separate world. graph() produces a pbx_jack::Graph — ports named node:port, links as connections, PipeWire's media class where JACK would have client metadata — so the model, the matrices, port groups, undo and the find bar work unchanged. Opening the PipeWire block swaps the source and the layout (layout-pw.json, with a camera per style); ← JACK swaps them back. The two graphs are never mixed, by design. On top of JACK the tab's clock is JACK's (rate and buffer size, rebuilt when either changes); the default quantum is shown apart, as what PipeWire uses on its own.

What it leaves to WirePlumber. PatchBox doesn't link desktop streams or keep PipeWire links in sessions. WirePlumber's policy does that, and a session restoring links over it would fight it (a browser would go silent when its auto-link was undone). That design is written down and deferred (section 18).

10patchboxd: the session daemon

patchboxd is an NSM server and a little more. It runs on one thread and one poll(), with no async runtime. Everything that can take time (clients saving, starting, stopping; git; hook scripts; jackdbus) is a step in an operation that waits with a deadline, so the loop never blocks. The window, patchbox-ctl and NSM clients with :server-control: all drive the same operations.

control socket NSM (OSC) SIGCHLD JACK (eventfd) operation steps

Everything is a file descriptor. SIGCHLD is blocked and read through a signalfd; libjack's notification thread writes to an eventfd; the OSC socket is bound to the loopback at a port the kernel picks, and clients get it in NSM_URL. The control socket speaks JSON lines tagged by cmd; a subscribed connection gets the daemon's State whenever it changes (diffed against the last one sent) and its log lines.

When it runs. The window starts patchboxd when none answers and reconnects if it restarts. The daemon outlives the window while a session is open, and with no session and no front end it exits after 30 s, unless connection rules exist: those hold whenever their ports appear, window or not. For sessions without the window there is a user unit (systemctl --user enable --now patchboxd) and patchbox-ctl.

11A session's life

Opening a session while another is open is the longest operation the daemon runs: it saves and leaves one session, then loads and enters another, keeping the clients that can carry on (NSM's :switch:). Every message below is one the daemon sends or waits for. On the left are the steps, with the deadline each one waits under.

control socket NSM over OSC fork / exec · signals exit (SIGCHLD) D-Bus (jackdbus) libjack

Leaving A. NSM clients get /nsm/client/save; plain programs get their save signal, if they have one, and their save hook runs. The session file is written atomically (.session.toml.tmp, then a rename), with the JACK connections and, if remembered, the JACK settings. An automatic snapshot commits the folder if anything changed, and the session's close.sh runs. Then the clients that can't switch are stopped. Before each one's stop signal the daemon asks jackdbus to take the process's JACK clients out of the graph (DetachProcess, JackBus), so its departure costs the graph no cycle; then SIGTERM, or its own stop signal, with 30 s before the step moves on. With another jackdbus, or none, a client is simply stopped.

Entering B. Reserve kept Carla: it announced :switch: and B has a client with the same id (or the same program), so Carla only gets /nsm/client/open with its new path. The Jack step puts B's server settings in place if it remembers any, before any client starts: on the running server when only the buffer size, the log settings or the CPU wake-up latency limit differ (Carla, still running, keeps its connections), else with a restart (section 7). New clients are started with NSM_URL in their environment and $SESSION_NAME, $SESSION_PATH, $CLIENT_ID, $JACK_CLIENT_NAME expanded in their arguments. An announce is matched to its client by pid, by a process it started (wrapper scripts), or by executable; a program started by hand with the daemon's NSM_URL joins the session.

Loaded. When every NSM client has replied (or its deadline passed), all get session_is_loaded, load.sh runs, and the session is open. A client that announces later gets session_is_loaded right after its open. Its JACK connections come back as its ports appear (section 13).

Clients

NSM clients and plain programs, side by side

  • Status: stopped · launching · opening · ready · saving · stopping · running (a plain program) · no-announce · error.
  • NSM: :dirty:, :optional-gui: (shown or hidden as saved), :progress:, :message:, :switch:, :server-control:.
  • Plain programs: a save signal (0: it can't), a stop signal (0: SIGTERM), an optional terminal emulator; an NSM client that never announces is run as one.
  • Stopping: before the stop signal (or a kill), the daemon asks jackdbus to take the process's JACK clients out of the graph (JackPatchbay.DetachProcess, JackBus), so the stop costs the graph no cycle. It never starts jackdbus for that, waits a second at most, and doesn't ask a jackdbus that didn't answer again for 10 s; without one, the client is stopped as before.
  • Logs: stdout and stderr to .patchbox/<id>.log, cut back past 4 MB, the previous run's kept as .log.1.
  • Removing: a client goes to the session's trash (its entry kept, its files untouched) and can be brought back; a running one is stopped first (saved first, if asked: a failed save leaves it in place). forget drops it for good, its files to the desktop Trash if asked. Deleted sessions and templates go to the desktop Trash too (freedesktop spec, with .trashinfo), never removed outright.
  • Updates: the state carries the protocol version and whether the daemon's program was replaced on disk (/proc/self/exe reads (deleted)). The window replaces an older daemon at once when no session is open, or offers Update (save, close, restart, reopen) when one is; with nobody connected, the daemon re-executes itself in place, same pid.

Snapshots, templates, scripts

Ideas from RaySession and others, done with git, folders and sh

  • Snapshots: a git directory beside the work tree (.patchbox-snapshots), unsigned commits and no hooks; audio, video and files over 50 MB excluded; a tag per snapshot. Automatic ones at save and close skip when nothing changed. Rewind stops the clients, resets the folder to a tag and opens the session again.
  • Session templates: a copy of a session folder; client templates: a client's command, properties and files, with its file prefix replaced by __CLIENT__.
  • Hook scripts: patchbox-scripts/{load,save,close}.sh in the session folder or one above it; the operation waits up to 60 s. Per-client start / save / stop hooks run beside the client and don't hold it up.

12On disk

Plain files a person can read: TOML for sessions, JSON for PatchBox's own settings, a git directory for history. Every file PatchBox writes is replaced atomically (a temporary file, then a rename), and every log it keeps is capped.

A session is a folder. Its session.toml lists the clients (command, NSM or not, signals, environment, label, whether it was running), the JACK connections with the ports present at the last save, and optionally the JACK settings. Clients keep their own files under the path NSM gave them, named after the application and the client id, which is what makes a session folder portable and lets client templates rename a client's files. The lock file stops two daemons from opening the same session.

13Connection memory and rules

Two kinds of connections persist, and both live in the daemon. A session's connection memory (RaySession's rules) restores what the session had, as each client's ports appear. Connection rules (qjackctl's persistent patchbay) hold globally, with * patterns, whether a session is open or not. Both act only when ports appear: a connection you remove by hand stays removed.

restore a saved pair guard against auto-connect the trigger

Why "a port new". Restoring every saved pair on every look would fight you: remove a connection during the session and the next client to start would bring it back. Restoring only pairs with a port that just appeared means a connection comes back when its client comes back, and not otherwise. The guard against auto-connect follows the same reasoning in reverse: a program that connects itself to system:playback on start, against what the session says, is undone. A connection between ports the session never knew is left alone.

Not for PipeWire's links. On pure PipeWire, undoing "auto-connections on new ports" would undo WirePlumber's stream links and a browser would go silent. PipeWire-aware sessions need different rules and are deferred by design (section 18).

14The window

One borderless GL window in Luluda's manner: a slim title bar, a row of grouped tiles (an icon over a label), a darker sidebar, and the canvas. Settings, rules, the event log and the session dialogs are pages drawn over the canvas, toggled from their buttons, so the chrome around them stays usable. Buttons are tinted by what they do: green starts, amber changes, red stops, blue opens.

Narrow windows. The toolbar measures its groups first and drops them by priority when the window is too narrow: the session buttons, then the views, the time display, the rate readout (the sidebar has it), the port types (they have keys), the transport. The JACK readouts stay. The interface scale (1.25 by default) multiplies the desktop's own, and text is rasterised at the exact pixel size, so it stays sharp at any scale or zoom.

15Footprint, measured

Light was a requirement, not an afterthought. These are measurements of the release build: binary sizes from the files, the composition from symbol sizes (unstripped), and runtime figures from PATCHBOX_STATS=1, which prints the first-frame time, memory, thread names and loaded libraries.

Static SDL, trimmed. SDL 3.4.18 is vendored, patched (the manual's "The static SDL") and linked statically with only what a Wayland GL window needs: no X11, no D-Bus, no audio, no joystick subsystems. Its C objects are built with section splitting, so the linker drops what PatchBox never calls. The package builds with !lto for makepkg's flags only, because GCC LTO bytecode in SDL's objects can't be read by Rust's linker; the Rust side keeps Cargo's own LTO.

Measured side by side. The run-time figures come from the nested test harness with a private jackdbus. Launch to first frame there is 190–280 ms today, for this build and for r62 alike, run alternately in the same harness; it showed ~90 ms when r62 was new, so the change is the test machine's, not PatchBox's. Heap and stacks (~20 MB), 15 threads and one wake a second at idle are as they were.

16Validation

No test touches the desktop's audio. The GUI runs in a nested KWin on a private session bus, inside a user, IPC, mount and PID namespace with its own tmpfs on /dev/shm, against its own JACK server. The live jackdbus's shared memory, sockets and SysV lock are not even visible from there. The rule comes from experience: a test server once unlinked a live server's segment.

Scripted, then looked at. PATCHBOX_TEST feeds synthetic SDL events (clicks, drags, keys, wheel) through the same handlers as real input, and can take screenshots along the way; PATCHBOX_SNAPSHOT writes the final frame to a PNG. Every UI change in this project was checked that way: the script drives the feature, the screenshot is read.

18Open items

What's left, what's proposed, and what was set aside on purpose.

A D-Bus client of its own

Proposed, not decided

  • zbus is the largest part of both binaries (~1.7 MB of the window's 6 MB with its async runtime) and five of its fifteen threads, for a few dozen jackdbus calls and two signals.
  • A small blocking client on the jackdbus worker would cover what's needed: the wire format, EXTERNAL auth, and the handful of signatures jackdbus uses (s, as, v of b/i/u/y/s, a(ysss), (bba(vs))). Linking the system's libdbus is the other way.
  • Only the transport changes; the mapping in server.rs and jackcfg.rs stays.

HiDPI on a real scaled screen

The one check the harness can't make

  • The nested KWin's virtual output can't be scaled (--scale is for windowed backends; kscreen-doctor needs KScreen's D-Bus backend).
  • The code follows SDL's pixel density and display scale, with the interface scale on top; it needs eyes on a 150 % or 200 % output.

PipeWire-aware sessions

Deferred: WirePlumber does its thing
